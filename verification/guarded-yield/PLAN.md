# Guarded foreground task yield, preregistered before implementation

Base d21e9ec2260f7c23e220a2e17baed81a5cf39380, deployed product and strengthened undo/reset tests unchanged. No main/deploy actions.

Reuse pre-existing healthy-frame policy: foreground starts with timers. Main thread requires uninterrupted visible frame delta and observed callback gap both positive and <=40ms for >=750ms after promotion. Only then allow MessageChannel wakes. One feedback message per actual foreground frame while allowed, and one revoke on transition to disallowed; no repeated disallowed traffic. Timestamp uses performance.timeOrigin+performance.now. Worker permits task wake only if latest healthy frame timestamp age is finite and 0..40ms. Any missing/stale/invalid/hidden signal falls back to original timer. Feedback requestId must match current generation; no change of requestId on feedback. Revoke/promotion/resume/cancel clear permission. Thus no reliable frame heartbeat means timers. No timer/slice/algorithm/physics/deadline changes, no faster background pacing. MessageChannel unavailable/failure uses timer. Close ports on wake/cancel/dispose.

48 fresh Chrome attempts: 12 cells × AB/BA two pairs. Two layouts (default3,swapped4), each has dwell0/6/26 normal, changing aim (6s then changed2s then final2s), dwell0 and6 at CDP CPU slowdown4. Rate is existing app rate1; slowdown4 is synthetic whole renderer load, not physical input. Three/four geometry fixed from prior harness, not new recall claim. Held-out stress conditions are load/transition; short4 work may finish before foreground and is explicitly a negative control. No skipped warmups, all errors/timeouts/capped outcomes retained. Fixed trusted pointer probes every250ms during aiming and search. Record successful trajectory/fullrest/nativeworld exact, post-rest wait, settings→route, Chrome process CPU lower-bound, all input event→rAF p95/worst/count>50/100ms, all frame gaps, permitted/revoked feedback counts and intervals. No extra worker trace instrumentation in performance runs. No threshold retuning after results.

Promotion requires every physical/pair/error and strengthened full UI gate pass; normal default3 dwell6 both pairs improve and mean wait reduction>=5%; no foreground-work cell mean wait >5% regression; candidate input→rAF p95 <=baseline+5ms and worst<=baseline+20ms in every cell with samples AND pooled, and no unexplained increase in >100ms incidence. Empty/no-work cells reported not used as proof. Process CPU no more than10% higher per cell (lower-bound limitations retained). Two pairs are a feasibility pilot, not population precision; any apparent pass needs further independent repeats, no automatic deployment. Failure or ambiguous benefit => stop and report, no post-hoc subset exemption. Any diagnostic rest-transition split preserves primary whole-search metrics.

Load detail: CPU4 is Chrome page-target Emulation.setCPUThrottlingRate(4), not a measured4× change of all processes/workers. It is a reproducible main/renderer pressure condition; report exactly that scope. Main→worker grant messages are counted with timestamps in the same Worker wrapper in both arms. No discarded transition samples. Existing native stage caps/deadlines can yield different finite-budget outcomes under stress; such outcomes fail the exact comparison and remain failures, not adjusted budgets.
