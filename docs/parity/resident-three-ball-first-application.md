# Genuine-three first application boundary (HOST/source)

This checkpoint connects the authenticated physical-before-application bank to
the first application boundary. It does **not** activate a runtime path, qualify
native whole-h parity, complete the latched outer step, or claim fully resident
recurrence. Three physical spheres remain three spheres; the cue shaft and head
remain dynamic roles 3 and 4.

## Authority and order

`src/physics.js`, `PhysicsLab.step`, is the application-order authority. With a
cue present, the outer call latches 64 subdivisions. Each inner h performs:

1. compliant tip/contact preparation;
2. the complete physical world step, including all dynamic post-CCD work and
   broad-phase post processing;
3. binary64 application `time += h`;
4. cue-obstruction observation;
5. collision-event draining;
6. angular-patch resistance for all balls;
7. timed cue withdrawal.

Only after all latched subdivisions does the original application restore the
outer dt, increment `steps`, and update outer distance/height/trail bookkeeping.
The convenience three-ball source wrapper is not authority for this ordering.
The earlier post-application component remains a component with its stated
scope; it has not been relabeled as the actual application boundary.

The new `three-ball-first-application.mjs` consumes a locally branded
`createThreeBallFirstPhysicalBroadPostPlan` and internally executes that exact
physical chain. The physical broad result and its nested physical result are
revalidated before application work. Candidate body, cache, journal, and cue
values come from those produced word banks, never from `sourceExpected`.

## Adopt the existing joint result, once

The source cue prefix and the physical cue owner are distinct stages. The
physical owner has already solved the actual two-dynamic cue joint. Application
adoption verifies the exact current 144-word joint input, completion and CCD
receipts, and pending cue-prefix state. It copies the existing sealed numerical
output and ten joint impulses into the cue bank and clears the pending-solve
flag. It does not run a second candidate joint solve. A repeat adoption fails.

All cue fields remain in the strict source comparison. In particular, original
lateral `applyImpulse` retains helper `torque` fields on its shaft/head objects.
Those are not native force/torque accumulators and are not joint inputs. Their
provenance is preserved by evaluating the unchanged original cue lateral
Number-program on authenticated initial inputs, retaining its shaft torque
output and the source head's null-point zero branch. No additional impulse is
applied. This is not a dropped-field comparison or an invented physical torque.
The source's cached world COM is deliberately not refreshed by joint adoption.

## Narrow no-emission admission, not a velocity shortcut

The admitted first application branch requires the produced journal to be
complete at sequence 1 with zero events and the exact three live floor edges.
Each edge must have the original floor identity, no cue flag, and an admitted
active single-point floor manifold/cache. Cue birth, removal, or touch emission
flags must be absent. Unknown edges, nonempty events, cue contacts, invalid
cache topology, missing physical predicates, or a timed withdrawal requirement
fail before the affected application publication.

Thus retained event history and game state are unchanged only after this
produced topology proof. No success/miss or `ThreeBallGame.finish` is invented.
This is not general event-drain, obstruction, or withdrawal support.

The exact Number-program clock is checked against the cue prefix's clock.
Application patches and scene queue transitions occur after the complete
physical broad boundary and the clock/observation/drain admission. The endpoint
has inner substep 1, retains the original outer `steps`, and retains all of the
authenticated created history.
