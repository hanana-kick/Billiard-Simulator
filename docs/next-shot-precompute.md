# Next-shot search during playback

The CPU controller can prepare the next search while the current physical shot is moving. The route inspector exposes a separate on/off switch. The existing search algorithm, route mode, targets (except normal next-cue target repair), numerical settings and physics laws are unchanged.

## Safety and resource contract

- The live Rapier world and live GameRules still own contacts, score, turn and final positions. Prediction never mutates them.
- A completed idle preview is reused only when its entire source world, settings, game snapshot and frozen shot rules match the shot being fired. Otherwise one isolated prediction Worker simulates to full physical rest, at most 30 seconds of physical time. An unfinished horizon is not a resting state and cannot start next-shot search.
- The projected game observes all contacts through rest, including late four-ball opponent or floor fouls. Next-cue target repair uses the same selection policy as the live controller.
- The live RAF loop stops on the first all-body-sleeping physics step. This avoids extra frame-dependent sleeping steps and makes the entire predicted state comparable at the same physical boundary.
- During motion, the entire solver coordinator, geometric planning and trial physics run in one Worker. No search planner runs on the playback thread. An unused coordinator is prepared while aiming (including initial loading), before a shot when possible; it contains only bundled code and initialized WASM, never a request or predicted state. During motion it uses a 1 ms cooperative work target with 16-step blocks and 12 ms yields. These are scheduling targets, not hard CPU-time guarantees. Nonfinal background progress is limited to once per 300 ms before constructing/cloning the full result. The prediction Worker uses 32-step blocks and 16 ms yields. Worker failure never falls back to main-thread physics during playback. One reported core disables speculative work.
- After the initial 250 ms, three frame delays above 40 ms (within 1.2 seconds) or a single delay above 120 ms suspend speculative search, preserving completed work until verified rest. This responds to actual playback pressure instead of trusting reported logical-core count.
- No speculative routes are published before actual rest. Promotion re-reads the current world and game, then compares raw Rapier snapshot bytes, physical metadata, all object states, prior events, settings, mode, selected cue and game state. Display-only trails, accumulated distance and max-height are excluded. Any discrepancy discards the entire speculative result.
- Reset, undo, new shots, changing relevant inputs/options/materials, pause, window blur/visibility interruption and disabling preparation cancel the generation. Late callbacks cannot revive it.
- A matched in-flight search becomes the ordinary foreground search inside the retained coordinator Worker, with the ordinary useful foreground concurrency. Completed outcomes, adaptive solver state, and the active physical evaluation are retained during pressure suspension. At verified rest a one-job dependency planner continues in the same initialized Worker at normal foreground duty (32 ms work target, 64-step blocks), without restarting its evaluation or creating a nested Worker. Parallel planners complete the retained evaluation and dispatch only the remaining wave to the normal pool. Cancel/new request/dispose still wake and discard the old evaluation exactly once; discarded partial steps are counted. The public message generation changes on suspension/promotion, while the private retained evaluation generation remains stable until cancellation. The ordinary worker plan is restored, including later Resume when a cached search had already finished. Empty-cache and later one-job Resume paths also reuse the initialized coordinator. A failed continuation disposes its retained evaluation and reports an error, never overwriting that error with a stale cached result.
- An empty but continuable cached search automatically gets one normal configured foreground budget at verified rest, retaining completed work. It does not automatically repeat that budget again. A verified cached route is shown without restarting.
- A prepared search may still have no solution or may require more time. It does not claim exhaustive infeasibility, instant results on every shot, or the best route. Normal partial results and Resume behavior remain.

## Validation

Unit and native-physics checks live in `tests/next-shot-precompute.cjs`, `tests/next-shot-lifecycle.cjs`, `tests/next-shot-optimizer.cjs`, and the background/promotion cases in `tests/worker-pool.cjs`. Browser cases live in `tests/e2e/next-shot-precompute.spec.cjs` and exercise the built real application with real Workers, narrow screens, cancellation, exact-state rejection and next-shot publication.

The implementation does not deploy or publish anything. Browser timing and complete-suite outcomes must be recorded with the final candidate; unit tests alone do not qualify a release.
