# Four-ball, search, rendering and table geometry

## Implemented
- Four-ball practice mode uses two cue balls and two red balls on the existing Rapier carom dimensions. It is not a claim of tournament-complete Korean rules: two distinct reds score +1; touching the other cue ball or the shooter leaving the table scores −1; negative totals are allowed; no finish target. A miss/foul changes cue; score retains cue. Manual cue selection, reset, and undo are available. Rules observe real contacts, never force velocities or positions. Free experiment mode retains arbitrary bodies and placement.
- Official shadcn Base UI was already present in the inspected v10 repository. All 16 vendored upstream Git blob hashes and generated import/icon-only transformations remain verified. New controls reuse those actual components; no substitute primitives or CDN runtime dependencies were added.
- Reverse contact-point/tangent proposals supplement existing mirrored-cushion seeds. Same-engine forward replay validates every candidate. Speed/elevation ranges, moving-target exclusion and worker count are available. This finite numerical search does not guarantee a global optimum. See search-method.md.
- Search uses bounded 1–4 worker pool, mobile maximum 2, independent worlds, deterministic per-count candidate partitions, cancellation, stale response rejection, merged progress/results and cooperative failure recovery. Changing worker count may change adaptive search exploration/results.
- WebGL rendering can run in a separate OffscreenCanvas worker. The main thread retains input/projection and presents transferred ImageBitmaps. Only one frame is in flight; later work is replaced with the latest state. Resize/DPR, geometry reuse, worker startup/error timeout, termination and CPU fallback are handled. No shared memory, hosting header or infrastructure changes.
- The rail/cushion corners use 45-degree joints and beveled profiles. CPU/GPU mesh triangles come from the actual Rapier convex hull. Nose height and playing area are unchanged.

## Frame ceiling follow-up, 2026-10-23
- Follow-up integrated suite: 134/134 passed with test-process concurrency bounded to 2; production build, typecheck and all 16 official component provenance checks passed. An earlier unbounded parallel run terminated one Rapier test process without an assertion report; the isolated case and bounded full run passed. The exact termination cause is not established.
- All main-render paths now use a single strict cadence gate: CPU fallback at most 30 fps; WebGL and OffscreenCanvas worker at most 60 fps. Physics keeps its separate fixed integration step. Worker completion only queues a bitmap; it never paints or submits another frame outside the gate. Hidden pages cancel RAF, discard completed bitmaps, and resume without physics catch-up or duplicate RAF registration.
- Actual cloud-browser CPU rendering counters, forcing dirty frames: 221 completed frames in 10,000.30 ms (22.10 fps). Hidden-tab interval: 47,665.5 ms, zero completed frames. Strict minimum spacing intentionally under-runs non-divisible refresh rates. Duplicate timestamps, repeated dirty notifications, mode changes and hidden/resume cannot bypass the gate.

## Default UI renewal
- The initial official-component integration still had a custom dark slate skin. The renewal removes it, restores neutral/light semantic tokens and default component styling, and composes game setup, score and hit-point controls as standard Cards. Application CSS now owns layout and simulation-specific hit surfaces, not component padding/color overrides.
- Mobile secondary scene-mode controls are available in settings rather than occupying a third canvas toolbar row. Custom explanatory text is at least 14px; coarse-pointer controls have a 44px minimum hit height. Advanced route settings start collapsed while the main route action remains visible.
- Real cloud-browser inspection used desktop and generic 320×568, 390×700, 844×390 CSS-pixel frames. Added automated resize sweep preserves world identity and aim state across portrait/landscape/fold-style dimensions. These are not measured Galaxy Fold8/Fold8 Ultra/S26 device viewports; actual Samsung Internet viewport, DPR, zoom and hardware behavior remain separate verification.
