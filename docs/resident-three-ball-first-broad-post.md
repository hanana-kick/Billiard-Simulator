# Genuine-three first postSolve broad/journal owner

This is a HOST-validated source-kernel component, **not a completed h, shot,
native parity qualification, or production admission**. No GPU was executed.

`three-ball-first-broad-post.mjs` accepts only a locally branded first-post plan.
It has two explicitly distinct profiles: the legacy partial component consumes
the post-application bank; the physical profile consumes all completed dynamic
post-CCD checks **before application**. Each public test executor obtains its
properly branded bank and scoped initial-inactive receipt internally. It does
not accept poses, later trees, journal snapshots, active sets, expected results, or general CCD authority.

The input bank already contains the resident-produced initial BVH/journal from
`three-ball-initial-broad.mjs`. The post owner reuses, without equation changes:

1. `rc_world_broad_begin_post`: current source awake chunk and original parent
   collider-list order (including recycled `[22,24,23]`, never a sorted order).
2. Separate bounds gather/evaluate/scatter, repeated for 25 fixed transport rows.
3. `rc_world_broad_commit_post` / `rc_bvh_set_aabbs`: original fat-box containment,
   allocator/refit/deferred-optimization state and pending updates.
4. `rc_world_broad_finish` / `rc_journal_finish`: partial owner seal only.

Before the journal acknowledges the already-executed genuine-three roster,
the kernel validates all 22 source body identities, complete ordered awake
entries, graph sequence/revision/epochs, all three edge endpoint generations
and lifetimes, the exact completed solver/CCD and selected boundary phases,
and the zero-transition profile. It does not replay the roster or set an
unchecked completion flag.

## Distinct native final-mass ordering profile

`createThreeBallFirstFinalMassBroadPostPlan(postPlan)` with
`executeThreeBallFirstFinalMassBroadPostForTest(plan,{testOnly:true})` retains the physical
pre-application boundary and adds exactly the missing native final mass refresh.
The previous legacy and physical component profiles remain separate and do not
silently acquire this behavior. `assertThreeBallFirstFinalMassBroadPostResult`
requires the exact newly branded result; the previous missing-COM witness is
still meaningful for the old profile.

Pinned Rapier `b716d375` `substep.rs:86–156` orders each current awake body's
collider/AABB harvest, then `update_world_mass_properties`, then the next body.
The new eight-stage descriptor repeats bounds gather/evaluate/scatter and mass
gather/evaluate/scatter for 25 fixed transport rows (152 calls including begin
and finish). Only the last harvested collider of each parent triggers mass work.
The original descriptor slot is read **before** broad scatter replaces it with
the actual collider index, preserving recycled generations and parent order.
All mass work must complete before the unchanged BVH `set_aabbs` and journal seal.
There is no host callback, future pose input, source-expected publication, or
second cue joint solve.

The sealed 256-word mass component supplies the unchanged original Init graph
prefix for outputs 0–11; its program is appended unchanged to the bounds program.
Sequential numerical stages reuse one scratch bank. It authenticates all five
real dynamic identities and local mass properties, consumes current generated
poses in the actual awake order, and publishes only canonical inverse mass
13–15, world inverse inertia 16–24, and world COM 59–61. It does not modify the
Cue/Joint source-component snapshot: application adoption owns that distinction.

`THREE_BALL_BROAD_POST_PROFILE=final-mass` exercises this profile. A test-only
microcode call observer compares every collider harvest → parent mass refresh →
BVH publication against independent original awake/parent-collider order. The
observer supplies no candidate values and the traced final bank must exactly
match the unobserved execution. Original full BVH/journal comparisons, immutable
scene/cue/roster/cache checks, non-mass canonical fields and fail-closed phase
checks remain active. This is HOST source evidence, not a GPU or whole-h claim.

Final-mass composition focused HOST gate: **5/5 PASS**; old physical and legacy
profiles also **5/5 PASS** independently. All runs include the three authentic
fixtures; call-trace identity is checked for each supported fixture. The plan
exposes the sealed component as `massPlan`, its absolute state as
`layout.massState`, and the distinct profile flag as `finalMass === true`.
