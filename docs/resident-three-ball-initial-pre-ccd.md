# Genuine-three initial pre-force CCD owner

The distinct initial-only owner consumes five actual dynamic rows (three spheres,
shaft, head), the authenticated initial CCD metadata and the produced current cue
prefix. It never creates a fourth sphere or accepts source future output.

## Original order and composition

`createThreeBallInitialPreCcdPlan(template)` provides 512 candidate words and the
unchanged `experimental-ccd-inactive.js` pre graph. The generated source accepts
absolute state/program/scratch bases. Its immutable stage schedule is split:

1. After cue prefix and registration, while scene/initialization phase is 1:
   `begin_cue`, gather/evaluate/scatter twice (shaft then head), `finish_cue`.
2. Caller executes original broad/BVH, narrow/floor and first-scene owners.
3. While scene/initialization phase is 2 and journal is pending sequence 1:
   `begin_spheres`, gather/evaluate/scatter three times in original sphere order,
   `finish`.

The owner cannot advance the scene itself. Cue completion is not all-five
completion. Mask bits are canonical roles0..4 regardless of check order. After
energy, the caller must reject any newly awake sphere not in checkedMask before
solver gather; this owner does not provide newly-awake prechecks. Entry sleep is sampled at each original boundary, before energy;
sleepers skip the source predicate. Canonical sphere force47 is the retained
source force, not userForce35. Cue force/torque are the original retained CCD
metadata, with explicit current alias validation. Cue bounds must agree across
actual numerical registration, scene and canonical tail; sphere bounds use their
own original registration/CCD fields, not unused cue-tail storage.

Active motion, malformed metadata, stale phases/generations, invalid output or
repeated use produce explicit unsupported status 4. Source strict motion `>` and
all 11 numerical outputs are retained. This does not provide an active CCD
splitter, post-CCD admission, a complete h, native GPU qualification or full-rest
qualification.

The isolated HOST harness uses actual candidate prefix/first-scene words at the
two boundaries. Its independent original source component expectations are only
comparisons. The runtime WGSL uses the unchanged resident numeric evaluator;
the HOST microcode harness alone uses the existing AST-approved numeric intrinsic.
